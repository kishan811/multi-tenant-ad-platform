1 Architecture

"Orchestration choice, extraction workers, how three connectors share ~70% of logic but differ in API quirks."

What I chose

Airflow as the orchestrator. One DAG per platform, with a single dynamically task-mapped extraction task (extract.expand(ad_account=...)) instead of one DAG per account. Each mapped task instance runs as an isolated pod (KubernetesPodOperator), does extract → normalize → tz-bucket → currency-convert → idempotent upsert, and writes its own extraction_run ledger row.

Why

  • Airflow is the orchestrator most data platform teams already run — the operational surface (retries, SLAs, backfill via dagrun re-runs) is well understood by whoever ends up on-call. I'd have picked Dagster's partitioned-asset model if this needed asset-level backfill as a first-class primitive, but it doesn't need to — correctness lives in the database's unique constraint, not the orchestrator. That's deliberate: the pipeline behaves identically whether it's run from Airflow, cron, or a laptop shell (exactly how this repo's own cli.py runs it).
  • Dynamic task mapping avoids a 7,500-DAG folder at 1,000 customers × ~2.5 accounts × 3 platforms — the DAG discovers active accounts from dim_ad_account at run time.
  • One task per (platform, ad_account) matches the platforms' own rate-limit granularity (per-account, not per-API-key) — a task's blast radius on a 429/RESOURCE_EXHAUSTED is exactly one account.
  • dags/google_ads_daily.py makes this concrete rather than only descriptive — real TaskFlow/dynamic-task-mapping syntax calling the exact same run_customer_extraction() that cli.py uses. It's illustrative, not run against a live Airflow scheduler (that needs real Airflow Connections and Pools, out of scope here) — see the Implementation tab's assumptions for that caveat spelled out.

How the 70% shared logic actually works

Implemented in base_connector.py. The shared base class owns pagination draining, retry/backoff with jitter, per-account rate-limiting, and auth-error classification. Each platform subclass implements exactly two methods: fetch_page() (the wire call) and parse_rows() (field mapping into the shared RawCampaignDayMetric contract). Adding Meta or TikTok next is a new subclass, not a rewrite of the pipeline.

Google Ads' specific quirks (vs. Meta, for contrast)

  • Cost is in micros (metrics.costMicros, an integer string — 1,000,000 micros = 1 currency unit) instead of Meta's decimal string ("1450.75"). Less locale ambiguity, but get the micros-to-cents divisor wrong and every number is off by orders of magnitude.
  • No platform-supplied finality flag. Meta tells you date_stop_is_final; Google Ads just silently revises metrics.conversions on re-query. Finality has to be inferred purely from row age (see Section 5).
  • Rate limiting gives no retry-after hint (RESOURCE_EXHAUSTED, no header) — the connector falls back to blind exponential backoff, unlike Meta's 613 error which at least suggests a wait time.
  • Pagination via nextPageToken in the response body, requiring the same GAQL query resent with a page token — a different shape than Meta's cursor object, same draining loop underneath.

2 Postgres schema

"Staging, fact, dimension tables; partitioning, indexing, retention; sample query for yesterday's spend in USD for customer X."

What I chose

Full DDL in migrations/001_init.sql. dim_customer / dim_ad_account / dim_campaign / dim_fx_rate as dimensions; stg_campaign_daily (append-only, monthly-partitioned, holds raw JSONB payloads) as the audit trail; fact_campaign_performance (monthly-partitioned on reporting_day) as the query surface, unique-keyed on (ad_account_id, campaign_sk, reporting_day).

Why this grain, why monthly partitions

  • The unique key on the fact table is the idempotency contract (Section 5) — it's not just a query-performance decision, it's a correctness one.
  • At 1,000 customers the fact table is only ~4.5M rows/year — not large enough to strictly need partitioning for speed, but partitioning turns staging retention into DROP PARTITION instead of a slow DELETE, and keeps dashboard queries pruning cleanly regardless of how many years accumulate.
  • A partial index WHERE NOT is_final keeps the reconciliation job's "which rows still need a re-check" query cheap and targeted instead of a full-table scan.

Sample query

WITH cust AS (
  SELECT customer_id, reporting_timezone
  FROM ads.dim_customer WHERE external_key = 'acme-d2c'
)
SELECT f.reporting_day,
       SUM(f.spend_minor_reporting) / 100.0 AS spend_usd,
       BOOL_AND(f.is_final) AS all_rows_final
FROM ads.fact_campaign_performance f
JOIN cust c USING (customer_id)
WHERE f.reporting_day = (now() AT TIME ZONE c.reporting_timezone)::date - 1
  AND f.reporting_currency = 'USD'
GROUP BY f.reporting_day;

Note all_rows_final is deliberately surfaced — a dashboard should say "$12,430 (still finalizing)" rather than presenting attribution-incomplete numbers as final.

3 Timezone handling

"Trace a single click at 11pm IST through extraction to the customer's reporting day. US DST? Reporting timezone changes triggering backfill?"

What I chose

The platform (not us) buckets a click into an account-local calendar day before we ever call the API — we only ever see report_date, never a raw timestamp. timezone_utils.account_day_to_reporting_day() converts that account-local day into the customer's reporting day by anchoring at local noon of report_date and converting that representative instant across timezones.

Why noon-anchoring, and where it's an approximation

  • We literally cannot recover the click's exact instant from a daily aggregate — noon is the best single representative point for a whole day, and it's exact whenever account_timezone == reporting_timezone (the common case for most D2C accounts).
  • It can be off by a day for a click near the account's local midnight when account tz and reporting tz differ enough to cross a day boundary — I call this out explicitly rather than hiding it, and the fix (hourly-grain extraction for the hourly-refresh cohort) is scoped as a documented next step, not a silent gap.
  • IANA tz names, never fixed UTC offsets — this is a one-line decision (account_timezone: str, not utc_offset_minutes: int) that eliminates DST bugs for free. Storing a fixed offset is the classic mistake that "works in testing" (run in a non-DST month) and silently misattributes a day every March/November in production.

Reporting timezone changes

A change writes a row to dim_customer_setting_history (backfill_status='pending') before updating the live config — the history row, not a config diff, is the source of truth that a backfill is owed. The backfill job re-runs the same pipeline with the new timezone and must explicitly supersede the old-bucketed rows for the affected range, since idempotent upsert alone doesn't handle a bucket shift (new key, not a collision) — this is the one place I had to add an explicit step beyond "just re-run it".

4 Currency handling

"FX rate source and granularity; store source / reporting / both; historical FX restatements; customer switches EUR → USD."

What I chose

Daily-close FX rates stored per-currency against a USD pivot in dim_fx_rate — any pair converts as a cross-rate, so I store n rates instead of n² pairs. Every fact row stores both spend_minor_source/source_currency and spend_minor_reporting/reporting_currency, plus fx_rate_used and fx_rate_date for full audit. See currency.py.

Why both, not just one

  • Storing only the converted number makes reconciliation against the platform UI impossible without re-deriving the original from a rate that may since have been restated.
  • Storing only the source number pushes conversion into every query — slower, and a correctness hazard if two dashboards convert with different rates.
  • All monetary math is integer minor units end to end, rounded exactly once with ROUND_HALF_EVEN (banker's rounding) — naive "always round up" rounding compounds a small systematic bias across millions of rows; this is proven by a dedicated test, not just asserted in a comment.

Restatements & EUR→USD switch

Because fx_rate_used is captured at write time, a later restatement of dim_fx_rate does not silently retroactively change history — propagating it is an explicit, auditable backfill above a materiality threshold. A currency switch uses the exact same dim_customer_setting_history event mechanism as a timezone change, but is actually simpler: it's an UPDATE of spend_minor_reporting on existing rows using their original fx_rate_date, not a bucket-shift — no orphaned-row problem.

5 Data accuracy

"Attribution windows revise data for 7–28 days; late-arriving data without re-pulling everything? Reconciliation against platform UI? Idempotency on worker crash?"

What I chose

A bounded rolling reconciliation window: every run re-pulls "yesterday" plus a trailing N-day window (N = MAX_ATTRIBUTION_WINDOW_DAYS, 30 for Google Ads here) for any account with rows not yet is_final. A partial index keeps that lookup cheap. Idempotency comes from a DB-level unique constraint plus INSERT ... ON CONFLICT DO UPDATE in one transaction per batch — see postgres_writer.py.

Why this, not a full re-pull

  • Spend/impressions are essentially final same-day; it's conversions that drift, so re-pulling everything on every run wastes API quota for no accuracy gain. A bounded window costs roughly constant work regardless of accumulated history.
  • Google Ads gives no finality signal at all — GoogleAdsConnector always reports "no veto" and is_final is purely days_old >= attribution_window_days. This is a real, acknowledged accuracy trade-off (contrast Meta's explicit flag), and it's specifically tested in tests/test_pipeline.py because getting the AND-combination wrong either breaks finality forever or defeats reconciliation entirely.
  • Idempotency by DB constraint + atomic upsert, never "check then insert" — that pattern races under concurrent workers. A worker crash mid-batch leaves the previous committed state untouched; re-running the whole batch is safe by construction.

Reconciliation against the platform UI

Designed, not built for this take-home: a low-frequency scheduled sampler that re-pulls a small set of already-is_final rows and diffs them against stored values — a nonzero diff on a row believed final is itself the alert. Scoped out to keep implementation time on the core path and its tests (see Section 9).

6 Operations

"Per-account rate limits across 1000 customers; expired tokens; observability and alerting; an on-call walkthrough for 'yesterday's numbers look wrong.'"

What I chose

  • Rate limits enforced per-account on every platform → task-per-account isolation is already rate-limit-isolated. Real risk at scale is thundering-herd, not per-account exhaustion — mitigated by jittered job start times plus a per-account token bucket as a second line of defense.
  • Expired/revoked credentials raise AuthError, a non-retryable exception class distinct from rate limits/transient errors (see base_connector.py) — the account is flagged and excluded from future extraction attempts until reconnected, rather than burning retry budget on a dead credential.

On-call walkthrough: "yesterday's numbers look wrong"

  1. Confirm "yesterday" means the same calendar day to the customer and to me, using their reporting_timezone — the Section 2 sample query is literally step one.
  2. Check is_final. If false, this is very likely not a bug — the conversion-lag window hasn't closed. Most "wrong number" reports should resolve here, via customer communication, not an engineering fix.
  3. If final and still disputed: replay stg_campaign_daily.raw_payload and compare against the platform's live UI. A live mismatch is a real gap (rare platform-side restatement outside the expected window).
  4. If raw payload matches the platform but the fact row doesn't match the raw payload: bug in normalize/convert/upsert — timezone_utils.py / currency.py are pure functions specifically so they're trivial to re-run by hand against the disputed row during an incident.

7 Cost

"API quotas, compute, Postgres growth; first place to cut cost at 1000 customers."

What I chose / would cut first

At 1,000 customers, API call volume (tens of thousands/day) and compute (a modest 20–50 concurrent task-slot pool) aren't the bottleneck — Postgres fact-table growth (~4.5M rows/year) is trivial for a managed instance too. The first real cost lever is raw_payload JSONB in staging: invaluable for on-call replay (Section 6 step 3 depends on it directly), but the largest storage line item relative to day-to-day value. I'd keep full retention for accounts with a recent dispute/anomaly flag and truncate more aggressively for clean-history accounts — targeted, not a blanket cut that sacrifices the exact debugging tool I rely on.

8 Implementation choices

Why Google Ads over Meta/TikTok as the implemented platform

Google Ads has the most distinct set of quirks to demonstrate the "70% shared, 30% platform-specific" architecture cleanly: integer micros instead of decimal strings, zero platform-supplied finality signal instead of an explicit flag, and no rate-limit retry hint instead of one. Implementing this one first means the hardest version of each design question (finality inference, backoff with no hint) is already solved, and adding Meta/TikTok afterward is strictly easier, not harder.

What's real vs. mocked

  • The Google Ads API is fully mocked (mock_google_ads_api.py) — pagination, rate limiting with no retry-after, expired/revoked auth, and conversion-lag maturation are all simulated deterministically, per the assignment's explicit allowance to avoid burning real credentials.
  • Everything downstream of the mock — timezone bucketing, currency conversion, idempotent upsert, the pipeline orchestration — runs against a real local Postgres (via docker-compose.yml), not just unit-tested against a double. See Section 11 for what that caught.

9 Next steps

What I'd build next if this went from a take-home into a real sprint, roughly in priority order.

Reconciliation job

The sampler described in Section 5 is designed, not built. This is the thing standing between "the pipeline looks correct" and "we caught the one time a platform silently restated old data." Highest priority.

Meta & TikTok connectors

Same BaseConnector contract, new fetch_page()/parse_rows() pair each. Should be a day of work, not a redesign — that's the whole point of Section 1's shared-logic split.

Hourly-grain extraction

For the refresh_cadence = hourly cohort, shrinks the timezone noon-anchoring approximation (Section 3) from up-to-a-day to up-to-an-hour.

Cold-storage tiering

Move fact_campaign_performance partitions older than ~13 months to cheaper storage, once actual growth data justifies it rather than a guess (Section 7).

Customer-day rollup table

A pre-aggregated table at the customer/day grain (skipping campaign) if dashboard query latency ever becomes a measured problem — not worth building preemptively at current row counts.

Real FX feed integration

Swap the hardcoded demo rate table for a daily pull from openexchangerates.org or the ECB reference rates into dim_fx_rate (Section 4).

10 ML extension / future use cases

Not part of the assignment, but worth a quick note on where this could go next.

Where this fits

The fact table is clean enough — one trusted row per customer/platform/account/campaign/day, with an explicit is_final flag — to double as a feature store later, if forecasting or anomaly detection ever becomes a priority.

Trusted campaign fact
        ↓
Feature engineering
        ↓
Customer/platform/day features
        ↓
Spend forecasting
Budget anomaly detection
Campaign performance prediction
        ↓
Model evaluation
        ↓
Production inference
        ↓
Monitoring / drift

Example features, all derivable from columns already in the schema: 7-day spend, 28-day spend, spend growth rate, CTR, CPC, conversion rate, rolling conversion trend, platform mix, campaign age, day-of-week, seasonality, lagged spend/conversions.

One caveat worth flagging up front

All feature calculations must be point-in-time correct to prevent data leakage, particularly because ad-platform attribution data can be revised after the initial reporting date — the same issue Section 5.1 covers for reporting, it just bites harder in a training set.

11 Bugs found while building this

All three were caught by actually running the pipeline against a live Postgres in Docker, not just by unit tests against fakes — which is the argument for doing that step at all.

Schema Partitioned table's primary key missing the partition column

ads.stg_campaign_daily is PARTITION BY RANGE (report_date), but its original PRIMARY KEY (id) didn't include report_date. Postgres rejects this outright: "unique constraint on partitioned table must include all partitioning columns."

Fix: PRIMARY KEY (id, report_date).

Found by: applying migrations/001_init.sql to a real Postgres container — the schema load failed outright, not a silent issue.

SQL ON CONFLICT DO UPDATE referenced a column name that doesn't exist

The upsert's DO UPDATE SET last_extraction_run_id = EXCLUDED.run_id was wrong — EXCLUDED is keyed by the table's actual column names, not by the Python parameter dict's key (run_id). The column is last_extraction_run_id, so it should read EXCLUDED.last_extraction_run_id.

Fix: corrected the EXCLUDED reference in postgres_writer.py.

Found by: running the CLI against real Postgres — psycopg.errors.UndefinedColumn: column excluded.run_id does not exist.

Driver behavior psycopg3's with conn: closes the connection, not just the transaction

Unlike psycopg2, using a psycopg3 Connection object directly as with self.conn: for transaction scoping also closes the physical connection on exit. The writer was reused across multiple customers in one CLI run — the first customer's upsert silently closed the connection, and the second customer's write failed with OperationalError: the connection is closed.

Fix: use with self.conn.transaction(): instead, which scopes just the transaction and leaves the connection open for reuse.

Found by: running the CLI across two configured customers in one process — a single-customer test run wouldn't have caught this at all.

1 Overview

This is a Google Ads connector that pulls campaign-level daily metrics, normalizes them for timezone and currency, and writes them into Postgres idempotently. The reasoning behind the full multi-platform system — Meta, Google Ads, and TikTok, orchestrated on Airflow — is in the Design Document tab above.

I mocked the Google Ads API rather than hitting the real thing (mock_google_ads_api.py), since the assignment says that's fine. The mock simulates pagination (nextPageToken), per-account rate limiting (RESOURCE_EXHAUSTED, with no retry-after hint), expired/revoked OAuth credentials, and conversion-lag revisions on re-pull.

4 Running the pipeline locally against a real Postgres

docker compose up -d postgres
# wait a few seconds for the healthcheck, then confirm the schema loaded:
docker compose logs postgres | grep "CREATE TABLE" | tail -5
export DATABASE_URL=postgresql://adpipeline:adpipeline@localhost:5433/adpipeline
python -m adpipeline.cli --start 2026-08-15 --end 2026-08-15 --today 2026-08-16

--today overrides "now" so the mock's reporting-lag simulation and FX-rate lookup stay deterministic for a demo run — leave it off to use the real current date.

Take a look at what landed:

docker exec -it $(docker compose ps -q postgres) psql -U adpipeline -d adpipeline -c "SELECT customer_id, ad_account_id, reporting_day, spend_minor_reporting, reporting_currency, conversions, is_final FROM ads.fact_campaign_performance ORDER BY reporting_day;"

Run the same command again — the row count shouldn't move, that's the idempotent upsert doing its job. Run it again with a much later --today (say --today 2026-09-20, past the 30-day Google Ads conversion-lag window this pipeline uses) and you should see conversions and is_final update in place on the same rows, still with no new rows created.

Tear it down with docker compose down -v when you're done.

7 Assumptions I made for this take-home

  • Google Ads is the platform I implemented. The design doc covers all three (Meta, Google Ads, TikTok); the base connector contract (base_connector.py) is written so adding Meta or TikTok later is a small addition, not a rewrite.
  • The API is mocked, which the assignment explicitly allows — no real ad credentials spent. The fixture reproduces the quirks the assignment specifically asks about: pagination, rate-limit responses (with no retry-after hint, unlike Meta), and conversion-lag revisions. (mock_google_ads_api.py's docstring spells out exactly what's simulated and how it differs from Meta.)
  • dim_customer/dim_ad_account are seeded from config/customers.yaml instead of a real onboarding flow, which doesn't exist for this exercise. cli.py's _ensure_dims upserts them idempotently on every run, so the whole demo is one command.
  • FX rates are a small hardcoded table (cli.py::_DEMO_FX_RATES) rather than a real daily-close feed. The Design Document's currency section covers what the real source would be (openexchangerates.org or the ECB daily rates) and how dim_fx_rate would actually get populated in production.
  • The conversion-lag window is fixed at 30 days (Google Ads' own default UI reporting window) instead of being configurable per platform or account — pipeline.py's MAX_ATTRIBUTION_WINDOW_DAYS is the one constant to change if you want it shorter or longer.
  • Google Ads doesn't give us a "this row is final" flag the way Meta's date_stop_is_final does — GoogleAdsConnector always defers to the pipeline, and finality ends up being purely a function of row age (pipeline.py::_to_fact_row). That's a genuine accuracy trade-off, not something skipped out of laziness — see the Design Document's data accuracy section for the reasoning.
  • Reconciliation against the platform UI is designed, not built. I scoped it out to keep the 6–10 hour implementation window focused on the core extract → normalize → convert → upsert path and its tests — in the spirit of the assignment's own "thoughtful incompleteness beats rushed completeness."
  • dags/google_ads_daily.py is illustrative, not a tested production DAG. It's real Airflow TaskFlow/dynamic-task-mapping syntax calling the exact same run_customer_extraction() that cli.py uses, so it's not a second implementation of the pipeline — but it's never been run against an actual Airflow scheduler (that would need real Airflow Connections and Pools configured, out of scope for this exercise). Treat it as "here's what the DAG would look like," not "this DAG has been verified end to end."
